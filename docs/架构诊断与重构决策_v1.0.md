### 1.2 必须处理的 4 类债

#### A. 双前端并存（最表层的乱）

| 位置 | 状态 | 问题 |
|---|---|---|
| `app/static/index.html`（18.7KB） | `app/main.py` 的 `GET /` 返回它 | 旧版单文件前端，Win11 Mica 风格，与 Vue 版功能重叠 |
| `frontend/`（Vue3+Vite） | `GET /` 不返回它，dist 未接入 FastAPI | 一套完整前端（侧栏/会话/SSE/消息渲染）实际上"跑起来了但用户看不到" |

`frontend/vite.config.js` 的注释还写着 `E:\financial-report-agent`，说明新前端是后来加的、没回头收拾旧的。

#### B. 工具层把"故障"和"无数据"都变成一句人话

`app/agent/tools_registry.py` 的 `execute_tool` 捕获所有异常后返回：

```python
{"reply": f"工具 {name} 执行失败：{e}", "meta": {"tool_error": str(e)}}
```

而 `app/agent/react_subgraph.py` 的 `_serialize_result` **只取 reply** 喂回 LLM。后果：模型看到的是"一句报错的中文"，无法区分「该公司无此数据（该换参数或换工具）」与「系统挂了（该放弃或降级）」，于是会重复调用、或在报告里绕过工具自己编。这是**"AI 编数字"最现实的一条路径**，比提示词约束重要得多。

#### C. 状态 schema 与实现不符（隐性 bug 的温床）

- `app/agent/state.py` 的 `AgentState` 声明了 query/history/intent/.../answer/meta，**没有声明 `plan` / `plan_index` / `collected`**；
- 而 `app/agent/plan_subgraph.py:50-51,61-62,78,86` 一直在读写这三个键。

LangGraph 的 TypedDict 不做运行时校验，所以"能跑"，但一旦上 checkpointer（持久化 / 人工介入）就会**静默丢字段**。

#### D. 依赖清单与代码不符

`requirements.txt` 缺 `langgraph` / `langchain-core` / `pydantic-settings`（代码强依赖：`app/agent/graph.py`、`app/core/config.py`），却列了**全项目没有任何 import 的 streamlit**；无版本上限、无 lock。新机器按 requirements 装出来的环境跑不起来。

### 1.5 修完上面之后剩下的 3 个功能 bug + 1 个结构问题

1. **流式对话不写记忆**：`app/api/agent.py:63-83` 的 `POST /chat` 会 `_memory.add(...)`，但 `:86-113` 的 `POST /chat/stream` **从不写**。而前端 `frontend/src/composables/useChat.js:100` 只调流式接口 → 实际使用中记忆永远是空的，多轮对话等于每轮重开。
2. **CORS 非法组合**：`app/main.py` 同时 `allow_origins=["*"]` 与 `allow_credentials=True`，浏览器规范禁止，凭据请求会被拒。
3. **`session_id` 是装饰品**：`AgentChatRequest.session_id`（`app/api/agent.py:36`）完全未使用，模块级 `_memory = Memory()` 是**全进程单例** → 所有用户共享一份对话历史。修法见 §4.1（会话状态应进 state / DB，而不是靠把 Memory 做成 tool）。
4. **import 期副作用**：`app/api/agent.py:20-21` 在模块导入时就 `Memory()` + `get_agent_graph()`（编译图）；`app/main.py:23` 的 `import app.tools.financial_tools` 会立即构造 `RagSearchTool` → 连 Chroma。结果是**任何 import 都会拉起一整套运行时**，测试无法隔离、冷启动变慢。修法：全部移到 FastAPI `lifespan`，工具注册改为显式 `register_all(registry)` 调用。

### 1.6 文档漂移

- `docs/财报解读Agent方案_v1.1.md` 写的是 **v1.1 目标态**，比代码领先一个版本：§6.1 的 8 节点 DAG、§5.1 的 6 个服务层模块（metric_resolver / metric_loader / formula_engine / anomaly_engine / dupont / cash_flow_quality）、§5.2 的 9 个工具、§8 的五层评测，**代码里基本都还没有**。

**关键决定（与你"整理为两个模块"一致）：**

1. `app/` → `backend/`。**但包名保留 `app`**（即 `backend/app/`），迁移的第一次提交做到 **零 import 改动**：`from app.xxx import` 全部继续有效，只需把 `backend/` 加进运行路径（`backend/pyproject.toml` 或 `PYTHONPATH=backend`）。包名重命名（`app` → `finagent`）单独一次机械 sed，不和结构迁移混在一起 —— 两个高风险动作混做，出问题无法归因。
2. `frontend/` 原地保留；FastAPI 改为托管 `frontend/dist`（SPA fallback），`GET /` 不再返回旧单文件页。
3. `app/static/index.html` **删除**（旧前端），并在 `.gitignore` 加 `frontend/dist`。
4. 运行期数据（`storage/ logs/ reports/`）留在仓库根，由 `settings` 提供路径，不塞进 `backend/`。

## 3. backend/ 的三种组织方案

三个方案都能容纳你后续要做的：报告子代理、RAG 评测、MCP、失败回退。差别在于**边界画在哪**，以及**迁移成本和长期自解释性**。

### 方案 A：经典分层（按技术职责切）

```
backend/
├── app/
│   ├── main.py                     # create_app + lifespan
│   ├── api/                        # 只做 HTTP 适配
│   │   ├── routes/{agent,financial,report}.py
│   │   └── schemas.py
│   ├── agent/                      # 「图」与编排
│   │   ├── state.py  graph.py  routing.py       # routing ← 原 classify.py
│   │   ├── react/            # 原 react_subgraph.py
│   │   ├── plan/             # 原 plan_subgraph.py
│   │   └── registry.py       # 原 tools_registry.py
│   ├── tools/                      # 注册给 LLM 的工具（§5.2）
│   │   ├── financial.py  report.py  rag.py
│   ├── services/                   # 不注册给 LLM 的服务层（§5.1）
│   │   ├── metric_resolver.py  metric_loader.py  formula_engine.py
│   │   ├── anomaly_engine.py   dupont.py  cash_flow_quality.py
│   ├── data/                       # 存储与数据源
│   │   ├── schema.py  repository.py  quality.py  textify.py  metric_scope.py
│   │   ├── datasource/  vector_store.py
│   ├── core/                       # config / llm / embedding / memory / logging / docx
│   ├── evals/                      # L0~L4
│   └── mcp/
├── scripts/  tests/
```

| 维度 | 评价 |
|---|---|
| 优点 | 概念最少、和 docs §5.1/§5.2 一一对齐；新人/新 AI 会话一眼能懂；迁移最省事（现有目录几乎不用动，只补 services/ 与 evals/） |
| 缺点 | `tools/` 与 `services/` 是一刀切的"横向层"，一个能力的代码被劈成 2~3 处（如"杜邦分析"：service 在 services、tool 在 tools、公式在 data）；`agent/` 会同时装"运行时"和"业务编排"，半年后必膨胀 |
| 多 agent 落点 | `agent/plan/` 里塞子代理，会和运行时混在一起 |
| 迁移成本 | **低**（≈ 0.5 天，主要是补目录 + 搬 4 个文件） |

### 方案 B：领域架构（按业务能力切）

```
backend/
├── app/
│   ├── main.py
│   ├── core/                       # config / llm / embedding / logging / storage
│   ├── financial/                  # 领域：财务数据
│   │   ├── models.py               # 原 data/schema.py
│   │   ├── repository.py
│   │   ├── ingest/                 # 原 data/datasource.py + scripts/fetch_slice.py
│   │   ├── quality.py  textify.py  scope.py
│   │   └── tools.py                # 对该领域暴露的 4 个 LLM 工具
│   ├── retrieval/                  # 领域：检索
│   │   ├── vector_store.py  bm25.py  reranker.py
│   │   └── tools.py
│   ├── report/                     # 领域：报告（未来多 agent 所在地）
│   │   ├── graph.py  dag.py
│   │   ├── agents/{loader,writer,reviewer}.py
│   │   ├── compliance.py  export.py
│   │   └── tools.py
│   ├── conversation/               # 领域：对话编排
│   │   ├── graph.py  routing.py  react.py  memory.py
│   ├── api/                        # 唯一接口层
│   ├── evals/  mcp/
```

| 维度 | 评价 |
|---|---|
| 优点 | 一个能力的全部代码在一个目录，改"报告"不用跨 6 个目录；天然支持"按领域并行开发"；多 agent 有明确的家（`report/agents/`） |
| 缺点 | 领域边界要一次定对，否则会出现 `financial/` 反向 import `report/` 的环形依赖；共享基础设施容易被随手塞进 `core/` 变成第二个垃圾场；和 docs 的"服务层/工具层"概念对不上，需要重新对齐文档 |
| 多 agent 落点 | 最好 |
| 迁移成本 | **中**（≈ 1 天，含 import 重写 + 全量烟测） |

### 方案 C：薄内核 + 领域包 + 显式 harness 层 ★ 推荐

在 B 的基础上，把**与业务无关的 Agent 运行时**单独抽成 `harness/`，把**对外暴露形态**单独抽成 `interfaces/`。

```
backend/
├── pyproject.toml                  # 依赖 + 版本上限 + 可选 lock
├── app/
│   ├── main.py                     # create_app + lifespan（惰性初始化，见 §1.5-④）
│   ├── interfaces/                 # ★ 只做「对外形态」，无业务
│   │   ├── http/{app.py, router.py, schemas.py, deps.py}
│   │   ├── mcp/server.py           # 未来：把能力暴露成 MCP（见 §4.4）
│   │   └── cli.py                  # 未来：脚本统一入口
│   ├── harness/                    # ★ Agent 运行时（与业务无关，可单测）
│   │   ├── llm.py                  # 原 core/llm_client.py（去掉 chat_stream）
│   │   ├── state.py                # AgentState + 校验（补 plan/collected）
│   │   ├── registry.py             # ToolSpec（协议无关：内部工具 / MCP 工具同一形状）
│   │   ├── invoke.py               # ★ 执行 = 参数校验 → 重试 → 熔断 → 结构化错误
│   │   ├── context.py              # ★ 每轮注入：记忆摘要 / 当前日期 / 口径清单 / artifact 索引
│   │   ├── memory.py               # 原 core/memory.py（只留短期 + 会话摘要）
│   │   └── trace.py                # ★ 每次 run 落 span（route/tool/tokens/latency）
│   ├── domains/
│   │   ├── financial/{models,repository,ingest/,quality,textify,scope,tools}.py
│   │   ├── retrieval/{vector,bm25,reranker,tools}.py
│   │   ├── report/{graph,agents/,compliance,export,tools}.py
│   │   └── conversation/{graph,routing,react}.py
│   ├── platform/{settings,embedding,storage,logging,docx}.py
│   └── evals/{l0_data_quality,l1_ground_truth,l2_metric_parsing,l3_query_accuracy,l4_report_quality,run_all}.py
├── scripts/                        # fetch_slice / seed_metric_dict / probe_* / l0_validate
└── tests/
```

**为什么推荐它：**

- 你的项目**不是普通 Web 应用**，它有两套性质不同的东西混在一起：① 确定性数据管线（akshare→SQLite→指标→L0 校验）；② 概率性 Agent 运行时（路由/工具循环/记忆/多 agent）。方案 A/B 都把这两者混在 `agent/` 或 `core/` 里，结果是"评测跑不起来、工具没法单独测"。方案 C 把它们分开后，`harness/` 可以脱离财报业务写单测，`domains/financial` 可以脱离 LLM 写单测 —— **这是让 L0~L4 评测能落地的物理前提**。
- `registry.py` 抽象成**协议无关的 ToolSpec**（name / json-schema / handler / timeout / retryable / side_effect），内部工具与未来的 MCP 工具是同一形状 → "万物皆 tool"才有统一入口，否则 MCP 一接就分裂成两套。
- `invoke.py` 是你现在最缺的东西（§1.2-B 的吞异常），单独一个文件不超过 150 行，但它是"不编数字"的地基。
- 每个 domain 内部结构同构（`models / service / tools`），**新增领域（如 `news/`、`macro/`）时照抄即可**，不需要重新设计。

**代价（诚实说）：**
- 目录层级比 A 深一层，前期会觉得"文件太碎"；→ 用 `backend/app/domains/financial/__init__.py` 做对外出口，调用方只 import 该出口。
- 多一层抽象意味着**必须先写 `ToolSpec` 和 `ToolResult` 两个小类型**，不能直接开干；→ 约半天，值得。
- `harness/` 与 `domains/` 的边界在第一周会有几次搬来搬去；→ 规则是"能不能脱离业务单测"。

### 3.4 三方案对比

| 维度 | A 分层 | B 领域 | **C 混合** |
|---|---|---|---|
| 与现有目录的距离 | 最近 | 远 | 中 |
| 迁移成本 | 低（0.5 天） | 中（1 天） | 中（1~1.5 天） |
| 与 docs §5.1/§5.2 对齐 | 最好 | 需改写文档 | 概念改名对齐（service→domain 内 service） |
| 多 agent 落点 | 差（混在 agent/） | 好 | **最好**（`domains/report/agents/`） |
| MCP 接入 | 需新增顶层 `mcp/` | 需新增顶层 `mcp/` | **内建**（`interfaces/mcp` + 协议无关 registry） |
| 失败回退有位置 | 否（散在 tools_registry） | 否 | **是**（`harness/invoke.py`） |
| 评测可独立运行 | 勉强 | 好 | **好**（平台层与业务层解耦） |
| 长期可维护性 | 中（agent/ 会膨胀） | 好 | **好** |

## 4. 对你六个架构问题的意见

### 4.1 "万物皆 tool" 与 memory 的矛盾 —— 你的直觉对，但结论要修正

**核心：不是"万物皆 tool"，而是"万物皆可调用，但不是万物都由模型决定何时调用"。**

| 类别 | 谁决定时机 | 例子 | 注册给 LLM？ |
|---|---|---|---|
| **Tool** | 模型（function calling） | `query_financials`、`compare_peers`、`generate_report` | 是 |
| **Context** | 框架（每轮固定注入） | 记忆摘要、当前日期、可用指标清单、已有 artifact 索引 | 否 |
| **Store** | 无人（后端实现细节） | SQLite、Chroma、文件 | 否 |

`memory` 不是一种东西，是三种：

- **读（recall / 注入）→ Context。** 不该做成 tool。理由就是你直觉的那条，但更准确：① 模型不一定会调（可靠性问题）；② 就算调了，也多一次 LLM round-trip（成本问题）；③ 记忆是"每轮都要"的全量依赖，不是"按需"的局部依赖 —— 这正是 context window 机制存在的理由。
- **写（记住某事实）→ 可以是 tool**（`remember_fact(content, category)`）。因为"什么值得记"需要语义判断，模型比规则强。**但**对话本身应该是**自动落库**的（`interfaces/http` 层写 DB），不依赖模型调用。
- **管理（清空 / 查看）→ API + UI**，不是 tool。

**更重要的一条（针对你的项目）：财报场景里长期记忆的价值很低，而"工作记忆"的价值极高。**
真正该存的是 *本次分析的工作状态*：已确认的公司、期次、口径（累计/单季/合并）、已取过的数、已发现的异常、已达成的口径澄清。这些应该是 **state + artifact cache**（`state["artifacts"]`），不是向量记忆。理由：向量记忆是"模糊召回"，而这里需要的是"精确复用"——你已经算过贵州茅台 2024FY 毛利率，就不该在写报告时再算一次、更不该让两个节点算出不同值。

> 具体建议：`app/core/memory.py` 的 `long_term` / `add_long_term` / `recall` 三个成员全仓库无调用方（已实测）。**建议直接砍掉长期记忆**，把短期记忆改成 `harness/context.py` 里的纯函数（`build_context(session_snapshot) -> list[dict]`），会话状态落 SQLite（表 `chat_session` / `chat_message`），`session_id` 才真正有意义。这是花半天解决 §1.5-③ 的最短路径。

### 4.2 RAG 对"非长文本、多数值"到底有没有用

**结论：作为"取数主路径"没用；作为"证据检索器"有用。而且你现在的语料类型决定了 —— 别把 RAG 当 RAG 用。**

为什么传统 RAG 在你的数据上会输：

| 原因 | 具体表现 |
|---|---|
| 切块破坏结构 | 财务表格按 500/100 字符切，一行"营业收入 2024 1,234,567 2023 1,100,000"被切断，语义崩塌 |
| 嵌入模型对数字不敏感 | `bge-base-zh` 对"1234567"与"1234568"几乎无区分度；而你的答案是数字 |
| top-k 不稳定 | 同一问题两次召回不同 chunk；而 SQL 是确定的 |
| 无法做数值计算 | "同比增长率多少"需要算，RAG 只能找现成的 |

**更该做的事（按性价比排序）：**

1. **取数走参数化，不走检索。** LLM 只输出结构化参数 `{company, metric, period, period_type, compare}`，后端拼 SQL/pandas。你的 docs §5.2 已经写了"query_sql 收窄到两张视图"，方向对，但**优先级应再提高：参数化优先，SQL 只做兜底，RAG 最后**。这也是 §8.1 的洞察的延伸 —— 指标来自结构化接口时，"指标提取准确率"测的是 akshare，不是你的系统。
2. **指标名解析用 BM25 + 别名表，不用向量。** 指标名是短词（"毛利率"/"销售毛利率"/"毛利"），`metric_alias` 精确匹配 + BM25 的 Top-1 会显著高于向量召回。docs §5.1 的 `metric_resolver` 就是这个，落地优先级应是**第一**（L2 评测直接测它）。
3. **行级序列化检索（row-to-text）作为过渡方案。** 把每期每指标渲染成一句带元数据的话："贵州茅台(600519) 2024FY 毛利率 91.2%，报告期 2024-12-31，合并口径"，入向量库。检索时**强制 where 过滤 company_id + period + 报告期类型**（你 docs §5.2 已要求）。这不是最优解，但比裸 RAG 强，且实现成本低（`app/data/textify.py` 已经有一半了）。
4. **RAG 该用在哪：年报 MD&A、风险提示、审计意见、行业新闻 —— 用于"引用证据"，不是"取数"。** 输出必须带 chunk_id 与出处，进报告时只能以"引用块"身份出现（docs §6.3 第 4 条已经写了）。
5. **进阶但要慎用：** 你的数据其实是天然的图（company → period → metric），很多"看起来需要多跳检索"的问题，用 SQL join 就解决了。GraphRAG 的收益在你这里主要来自**关系定义清晰**，而不是向量。真正值得做的是"指标血缘/依赖图"（用于溯源和异常传播），这东西比向量 RAG 更契合你的合规需求。

**评测前提（这条最重要）：先建 L3（结果集比对），再谈 RAG 好坏。** 没有 L3，任何"RAG 有没有用"的讨论都会变成感觉。L2 测解析、L3 测取数、L4 测成稿，三层到位后，RAG 的边际贡献是**可以用数字说话**的（比如：去掉 RAG，L3 多少？L4 的"无来源数字数"多少？）。

### 4.3 单 agent + report 阶段多 agent —— 方向对，但要加一条硬约束

**你的设计是对的（入口单 agent、写作阶段生成子代理），但"子代理之间自由协作"在你的领域是负资产。**

原因：多 agent 的收益来自"并行、上下文隔离、专业分工"；成本是"通信开销、全局一致性丢失、不可复现"。而财报报告有两个硬约束——**数字可溯源**（docs §6.3 白名单）与**可评测**（§8 L4），恰恰和自由协商冲突：子代理 A 说毛利率 25.31%，子代理 B 转述成"约 25%"，白名单校验就会失败；而失败原因你无法归因到哪个 agent。

**建议：确定性编排 + 局部 agent 自主。**

```
口径解析（LLM 输出结构化参数）
   ├─ 指标装载（纯函数/SQL）        ┐
   ├─ 文本证据检索（工具）          ├─ 并行，全是确定性节点
   ├─ 同行画像（SQL）               │
   └─ 杜邦/现金流（公式引擎）       ┘
                ↓（扇入，形成白名单 whitelist + 证据 evidence）
        ┌───────────────────────────────────────┐
        │ 撰写阶段：这里是「子代理」唯一该出现的地方 │
        │  overview_agent   ← 只能写 artifacts.overview │
        │  metrics_agent    ← 只能写 artifacts.metrics  │
        │  anomaly_agent    ← 只能写 artifacts.anomaly  │
        │  risk_agent       ← 只能写 artifacts.risk     │
        └───────────────────────────────────────┘
                ↓
        合规审查（脚本，非 LLM）→ 不通过则定向重写（最多 2 轮）
```

三条硬规则：

1. **子代理之间不对话，只读写共享黑板的具名槽位。** 每个 sub-agent 的写入 scope 是 `state["artifacts"][own_key]`，别人只能读。这既保证并发安全，又保证"哪个 agent 写了什么"可审计。
2. **子代理的输入是白名单，不是自由上下文。** 写作 sub-agent 只拿到"它这一节需要的数字 + 证据片段"，拿不到全量报告。这既省 token，又天然防止跨节串数。
3. **子代理的输出是结构化 artifact，不是 Markdown。** `{section_id, paragraphs: [{text, number_refs: [...], chunk_refs: [...]}]}`，渲染成 Markdown 是最后一步。这样 L4 评测可以直接读结构，不需要正则抠数字。

**什么时候才需要"真协作"**：跨公司对比报告（多家公司并行分析后合并）。这时子代理之间需要口径一致性仲裁 —— 用"共享 artifact + 冲突检测器（同一 metric 不同值即报警）"解决，**依然不需要自由对话**。

一句话：**你要做的不是"多 agent 协作框架"，而是"一个可审计的多角色写作流水线"。**

### 4.4 MCP 模块 —— 先 server 后 client

- **定位**：MCP 是"工具/资源/提示词的进程间协议"。它的真实价值有两个：① 把你的数据能力暴露给外部（Claude Desktop / IDE / 别的 agent）；② 接入外部数据源而不改你的代码。
- **现阶段（单人、单机、演示性质）**：内部收益很小 —— 你完全可以在进程内调函数。但**对外收益很大**：一个 `financial-mcp` server 暴露 5 个只读工具（`query_financials` / `compare_peers` / `detect_anomalies` / `dupont_analysis` / `describe_schema`），是很好的作品集加分项，成本约 1 天。
- **顺序建议：先 server（对外），后 client（对内）。** 理由：client 会引入"工具来自外部、不可信、不稳定、可能无限慢"的复杂度，而你现在连内部工具的失败回退都还没做完（§4.5）。先把内部闭环做扎实。
- **架构上最重要的一点**：MCP 工具与内部工具必须**归一化成同一个 `ToolSpec`** 进同一个 registry。否则接 MCP 那天，你的 ReAct 循环、参数校验、失败回退、评测会全部裂成两套。这就是方案 C 里 `harness/registry.py` 存在的理由。
- **目录**：`backend/app/interfaces/mcp/server.py`（对外暴露），未来 `backend/app/harness/mcp_client.py`（对内接入）。
- **注意**：MCP 默认只读友好，`generate_report` 这类有副作用的工具走 MCP 时要单独标注 `side_effect=True`，并在 server 层加白名单。

### 4.5 tool 调用失败回退 —— 你现在这里是个真 bug，不是"没设计"

**先修 bug**：`execute_tool` 不要把异常转成 `reply` 字符串（§1.2-B）。改成结构化返回：

```python
@dataclass
class ToolResult:
    ok: bool
    data: Any | None = None
    error: ToolError | None = None   # code, message, retryable, hint, tool_name

@dataclass
class ToolError:
    code: str          # INVALID_ARGS | NO_DATA | TIMEOUT | UPSTREAM_ERROR | RATE_LIMIT | INTERNAL
    message: str
    retryable: bool
    hint: str          # 给模型的可执行建议，例如「该公司无此期次数据，可改用 period=2024FY」
```

**分级回退（按性价比从上到下，前三级必做）：**

| 级别 | 机制 | 落点 | 成本 |
|---|---|---|---|
| L1 | **参数校验前置**：JSON Schema/pydantic 校验失败不执行，直接把校验错误回给模型改参数 | `harness/invoke.py` | 半天，收益最大 |
| L2 | **有界重试**：仅 `retryable=True` 且幂等（查询类）时 tenacity 退避重试 2 次 | `harness/invoke.py` | 1 小时 |
| L3 | **降级链**：`query_financials` 失败 → `query_sql`（收窄视图）→ 文本证据 → 显式"数据缺失" | 工具配置里声明 `fallback=[...]` | 1 天 |
| L4 | **熔断**：同一工具同轮连续失败 N=2 次，本轮禁用并注入"该工具当前不可用，请换路径" | `harness/invoke.py` | 半天，防 ReAct 死循环烧钱 |
| L5 | **澄清/拒答**：`INVALID_ARGS` 且涉及歧义（公司/期次/口径）时，反问而非猜 | `domains/conversation` | 依赖 §8-L4 拒答评测 |

**两个容易漏的点：**
1. **错误要进 trace 和评测**：`tool_error_rate` 应是独立指标（按工具、按错误码），否则降级链坏了你也不知道。
2. **`NO_DATA` 不是错误**：库内确实没有这家公司/这个期次时，应返回 `ok=True, data={"missing": [...]}`，让模型在报告里写"数据缺失"（docs §6.4 有这条合规要求）。把 `NO_DATA` 当错误会导致模型重试到死或绕过工具。

### 4.6 "各种最新的 harness 技术" —— 值得抄的与别急着抄的

**值得抄（按对你的收益排序）：**

1. **结构化输出强约束**：用 pydantic schema + `response_format=json_schema`（或 tool-call schema）替代你现在的 `chat_json` 裸解析。`app/agent/classify.py` 是最大受益点（intent/task_type/entities 现在靠 prompt 约束，偶发解析失败就整轮挂）。
2. **工具结果"引用化"**：工具返回大结果时，正文只放 `artifact_id` + 摘要，让模型需要时再取（你的 `MAX_TOOL_CONTENT=1500` 是全局硬截断，会把表格截断一半，导致模型看到残缺数据还接着编）。这是**报告场景最关键的 harness 技术**，比任何 prompt 技巧都重要。
3. **上下文预算管理**：按 tool 配置截断策略（表格保留表头 + 前 N 行 + "共 M 行"；文本保留首尾），而不是全局 1500 字符。
4. **State checkpoint + Human-in-the-loop**：LangGraph 的 checkpointer 你已装（`langgraph-checkpoint 4.2.0`）。用于：口径歧义时暂停等用户澄清；报告生成中断后可恢复。
5. **Trace/可观测**：每次 run 一个 span（route、tool、tokens、latency、cost），落 JSONL。**这是你做 RAG A/B 评测的数据来源**，比"感觉变好了"有用。
6. **Eval gate 进 CI**：docs §8.4 已经有了，缺的是执行。门禁要有 baseline 文件，否则"跑一遍看看"不会发生。

**现在别抄：**

| 技术 | 为什么不 |
|---|---|
| AutoGen / CrewAI 类多 agent 框架 | 自由协商与 §6.3 数字溯源直接冲突；你需要的编排 LangGraph 已经够了 |
| 复杂 Reflection / 自我批判循环 | 在结构化数据上收益低（数据对不对不靠"再想一遍"，靠 L0/L3 校验）；徒增 token |
| 向量长期记忆 | 见 §4.1：无调用方、场景价值低、还在 import 期加载模型 |
| 自建 Agent DSL / 编排引擎 | 已有 LangGraph，自建是纯负收益 |
| 端到端"PDF 解析→指标"流水线 | docs §10 已经判过：指标走结构化接口，PDF 只用于 L1 人工核真值 |
